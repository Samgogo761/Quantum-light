## 3. 必须修正的预算表述

### R1：8.78–9.92 h 不是核心循环预算，也不是完整双路径实测

新增 q8_m0_gamma12_cuda_block_benchmark_20261006.py 的 main 在第 128 行保留惰性 NpzFile；第 50 行及 run_size 多次访问压缩数组，会反复解压完整数组。total_start 又覆盖这些读取。并行审查实测 slice_block 的读取/切片约 61 ms，预先物化为字典后约 0.029 ms（仅说明重复解压，非通用性能常数）。

16 步总 wall 还包括每次上传初态/顶点、末态下载。直接乘 576，相当于把这些一次性成本重复计算 576 遍；长作业本来应让状态驻留设备。同时，真实长作业的装配、全时顶点准备、存盘和调度还未计入。两种偏差不能简单相消。

run_size 只跑 vdp/kp（有泵 2T 代数窗）；双路径时间是乘二，不是 measured driven+undriven pair。

所以 8.78–9.92 h 可保留为旧短测算术外推，但不能写成“核心计算时间再加开销”、严格保守上界或服务器 wall-time 依据，也不足以选出最终最佳块大小。原交接单禁止直接用它申请全作业配额，这一点正确。

建议真实成本模型：
总时长 = 一次公共准备 + 各块(装配/读取 + 上传 + 有泵循环 + 无泵循环 + 下载/落盘) + 合并。
循环项按较长连续步数测；一次性成本单列。不可从 16 步的整体 wall 统一按步数放大。

### R2：吞吐原始账没有独立保存

新增 benchmark 只打印 stdout；结果目录中未找到对应原始 block benchmark JSON，摘要保留了两次总 wall 和最优概要，但没保留所有重复的 setup/loop/readback 分项。下一轮把原始 repeats、fixture/hash、配置直接写入新目录，再生成摘要。此缺口不否定已独立复现的后端正确性。

### R3：当前 worker 仍是短测脚本，尚非完整分块 runner

q8_m0_p1_h2_finite_kcv_gamma12_block_worker_20261006.py 每次从头构造 Gamma12、求积和顶点；含暗列时重新构造暗基，默认只取 64 列；时间长度仍来自 16 步短测常量。输出只有 delta_u/v、freq 和 n_point，尚无完整全局列清单、重复/遗漏检查、共享缓存和 merge 实现。np.savez_compressed 对已有路径会覆盖，正式 runner 需排他写入或明确恢复策略。

这是待完成工程，并非另一 AI 已声称完成的功能。不要直接把这个 worker 改一个循环长度就批量投放。
